# Kernel Fixer

此技能旨在通过“诊断-修复-验证”循环，自主解决内核编译失败的问题。

## 工作流程

### 1. 诊断问题 (Locate)
- 使用 `gh run list --limit 1` 获取最近失败的任务 ID。
- 使用 `gh run view <ID> --log-failed` 定位具体的编译器错误消息（如缺少头文件、语法错误、工具链冲突等）。

### 2. 查阅与记录历史 (Document)
- 检查根目录下是否存在 `build_error.md`。
- **对比**：读取 `build_error.md`，对比当前错误与以往记录，避免陷入无效的重复修改。
- **记录**：将当前错误的时间戳、错误描述及拟议修复方案 **追加** 到 `build_error.md` 末尾。格式如下：
  ```markdown
  ## [YYYY-MM-DD HH:MM] 错误诊断
  - **错误原文**: `...`
  - **原因分析**: `...`
  - **修复对策**: `...`
  ```

### 3. 执行修复 (Fix)
- 根据诊断结果修改代码、配置文件或工作流文件。
- 如果是缺少依赖，考虑更新工作流。
- 如果是源码冲突或语法错误，直接修改源文件。

### 4. 一次性提交 (Commit)
- 将所有改动（包括代码修复、工作流更新、`build_error.md` 的追加内容）一次性提交。
- **严禁创建多个提交** 以防触发过多的 CI 并行任务。
- `git add . && git commit -m "Fix: [简短描述错误原因]" && git push origin <current_branch>`

### 5. 监听与循环 (Verify & Loop)
- 使用 `gh run watch <NEW_ID>` 实时监控新触发的编译任务。
- **结果判定**：
  - **失败**：回到步骤 1，分析新的错误日志。
  - **成功**：向用户报告修复完成，并提供 `build_error.md` 的摘要。

## 核心原则
- **追加而非覆盖**：绝对不要覆盖 `build_error.md`，它必须保留完整的排错历史。
- **原子提交**：所有相关文件的修改必须包含在同一个 commit 中。
- **自主性**：除非遇到无法解决的架构性冲突，否则应持续尝试不同的修复方案。
